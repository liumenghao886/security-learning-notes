
# 第一部分：先分清两者
## 1.1 核心区别
|维度|	CSRF|	SSRF|
|---|---|---|
|借用的资源|	受害者浏览器的 Cookie|	服务器的网络访问能力|
|请求发起方|	受害者的浏览器	|服务器自己|
|攻击者位置|	第三方页面|	提交一个 URL 参数|
|受害者是谁|	用户（权限被滥用）|	服务器 / 内网|
|典型载荷|	 自动提交表单|	url=http://127.0.0.1:6379/|
|防御核心|	Token + SameSite|	白名单 + 网络隔离|

## 1.2 一句话记忆

```
CSRF：我让【你】做      —— 借用用户的会话身份
SSRF：我让【你替我做】  —— 借用服务器的网络位置
XSS ：我让【页面】做    —— 借用浏览器的代码执行权

三者都叫"伪造"，但伪造的对象完全不同：
   CSRF 伪造的是"用户的意图"
   SSRF 伪造的是"服务器的请求"
```
## 1.3 三方视角对照
|CSRF|	SSRF|
|---|---|
|攻击者做什么|	写一个会自动发请求的页面|	找到一个能填 URL 的功能点|
|受害者遭遇什么	|打开页面，浏览器自动带 Cookie 发请求|	服务器替攻击者访问内网|
|服务器失误在哪	|只看 Cookie，不问"是不是用户本意"	|用户可控 URL，服务器照单全收|

# 第二部分：CSRF 详解
## 2.1 成立的三个条件（缺一不可）
```
① 有敏感操作（转账、改密、发帖、删除）
② 身份凭证自动携带（Cookie 会随请求自动发送）
③ 服务器只凭 Cookie 判断身份（没有额外校验）
```
- 本质：服务器信任的是「会话」，不是「人」。


## 2.2 为什么同源策略挡不住
- 关键认知：同源策略限制「读」，不限制「发」。

|行为|	同源策略管不管|
|---|---|
|别的网站向你的站发请求|	❌ 不管|
|别的网站读你站的响应内容	|✅ 管|
|别的网站读你站的 Cookie	|✅ 管|
|请求自动携带目标域的 Cookie	|❌ 不管（这是 CSRF 的入口）|

- 攻击者不需要「拿到」Cookie，只需要「让 Cookie 被用上」。

## 2.3 GET 型 vs POST 型 vs Token
|模块|	本质|	利用方式|
|---|---|---|
|CSRF (GET)	|用 GET 发起的 CSRF| 一行搞定|
|CSRF (POST)	|用 POST 发起的 |CSRF	自动提交表单|
|CSRF (Token)	|加上 Token 校验	|前两种都失效|

## 2.4 防御体系
|层	|手段|	挡住什么|
|---|---|---|
|核心|	CSRF Token	|攻击者猜不到的随机值|
|浏览器层	|SameSite=Lax/Strict	|跨站请求不带 Cookie|
|业务层	|高危操作二次验证（旧密码/验证码）|	会话已泄露的场景|
|辅助|	Origin / Referer 校验|	简单的跨站请求|
## 2.5 常见误区
|误区|真相|
|---|---|
|"POST 比 GET 安全"|	❌ POST 型 CSRF 一样成功，安全在有没有 Token|
|"加了验证码就安全"	|⚠️ 验证码防自动化，但攻击者可自动化调用验证码接口|
|"HTTPS 就安全"	|❌ 毫无关系，HTTPS 防监听，不防 CSRF|
|"校验 Referer 就够了"|	⚠️ 可行但不稳（隐私设置剥离）|
|"Token 能防 XSS"	|❌ 完全不能，XSS 反而能拿 Token|
# 第三部分：SSRF 详解

## 3.1 原理
- 服务器上有功能会「根据用户给的 URL 去访问内容」：
- 攻击者提交的 URL 不一定指向公网——只要服务器能访问到，攻击者就能访问到。
|功能	|服务器行为|
|---|---|
|图片抓取 | 远程头像|	file_get_contents($url)|
|网页预览 | 标题抓取	curl 请求|
|RSS 订阅	|抓取 feed|
|短链还原|	跟随跳转|
|PDF图生成|	无头浏览器访问|
|Webhook	|回调 URL|
## 3.2 为什么危险：服务器在内网
```
攻击者视角：只能看到公网
服务器视角：
  ├─ 外网（为了抓网页）
  ├─ 127.0.0.1      ← 本机所有服务
  ├─ 192.168.x.x    ← 内网所有机器
  └─ 169.254.x.x    ← 云元数据 ← 最危险
```
- 服务器的 IP 本身就受内网信任。

## 3.3 URL 的五种形态

|类型	|示例	|用途|
|---|---|---|
|探本机端口|http://127.0.0.1:6379/ |发现内网服务|
|探内网	|http://192.168.1.10:8080/ |横向扫描|
|云元数据	|http://100.100.100.200/latest/meta-data/ |拿云账号密钥|
|读文件	|file:///etc/passwd|	读源码/密码|
|构造 TCP 包|	gopher://127.0.0.1:6379/_...|	完整模拟协议|
## 3.4 防御

|层|	措施|
|---|---|---|
|协议	|只允许 http/https，禁止 file/gopher|
|IP|解析后用真实 IP 校验（用 filter_var，不是字符串匹配）|
|重定向|	禁止跟随，或每次跳转重新校验|
|网络|应用服务器禁止出网（走代理）|
|云	|元数据启用 IMDSv2（需 token，SSRF 直接拿不到）|
- 核心原则：SSRF 的防御在「白名单 + 网络隔离」，不在「黑名单」。
## 3.5 Redis（最常被打的内网服务）
- 是什么： 一个内存数据库，数据全在内存，读写微秒级。
## 3.6 gopher 协议
- 能发送任意原始 TCP 数据，等于完整模拟协议通信。

# 第四部分：CSRF vs SSRF 对照总结
## 4.1 攻击链对照
```
CSRF：
  攻击者写攻击页 → 受害者打开 → 浏览器自动带 Cookie 发请求
                                          ↓
                              服务器只认 Cookie → 执行
                                          ↓
                              用户身份被借用 → 敏感操作发生

SSRF：
  攻击者找到一个 URL 参数 → 提交内网地址
                                    ↓
                        服务器替攻击者去访问
                                    ↓
                        内网服务被访问 / 元数据被读
                                    ↓
                        云账号或服务器被接管
```
## 4.2 三个必要条件对照
|CSRF|	SSRF|
|---|---|
|条件1	|敏感操作|	有接受 URL 的功能|
|条件2	|凭证自动携带|	服务器能访问内网|
|条件3|	只看 Cookie 判断身份|	没有校验 URL 目标|
## 4.3 危害等级对照
|CSRF	|SSRF|
|---|---|
|信息泄露|	低（只能改数据）|	高（读内网/文件/元数据）|
|权限提升|	用户级 → 用户自己的权限	|内网 → 服务器 root / 云账号|
|持久化|	低（一次性操作）|	高（写文件、写 crontab）|
|自动化|	高（一行 HTML）|	高（一个 URL）|

## 4.4 修复对照
|CSRF	|SSRF|
|---|---|
|核心手段	|CSRF Token	|URL 白名单|
|辅助手段	|SameSite、二次验证	|协议限制、禁止重定向、网络隔离|
|修复位置	|所有写操作接口	|所有接受 URL 的功能|
|检测手段|	检查 Referer、看登录态|	看服务器出网日志|
## 4.5记住一句话
```
CSRF：让受害者的浏览器"替"攻击者发请求
SSRF：让服务器"替"攻击者发请求

CSRF 伪装的是"用户的身份"
SSRF 伪装的是"服务器的身份"

CSRF 的攻击对象是"人（用户的权限）"
SSRF 的攻击对象是"机器（服务器/内网）"
```
